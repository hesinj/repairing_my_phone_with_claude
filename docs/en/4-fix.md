# The fix, step by step

This is what was done on the reference phone, with the checks that were made. Read all of it before you run anything.

## Before you start

* **Only if the kernel log shows the pattern** (see the [README](../../README.md)): the I2C error on bus 3 and the failed `drv260x` probe.
  The same symptoms with a different log have a different cause.
* **An unlocked bootloader.** The modified image has no AVB footer; an unlocked bootloader starts it with the orange warning, a locked one
  will not.
* `adb` and `fastboot` (Android platform-tools), Python 3, and AOSP's `mkbootimg` folder
  (`git clone https://android.googlesource.com/platform/system/tools/mkbootimg`; the OrangeFox 12.1 tree has it as
  `system/tools/mkbootimg`).
* **The boot image of the ROM that is installed**, exactly that build. On the reference phone: `boot-toco_20260609_1626.img` from the
  PixelOS release of 9 June 2026 (sha256 `6c966951f4a5dda25ff435f05b0e991da31647ccf4b7148690e6f444f1614813`), which was found identical
  to the installed `boot` partition by hashing both. If you only have the partition, dump it
  (`adb shell dd if=/dev/block/bootdevice/by-name/boot ...` from a recovery with root adb).
* **Your data, copied first if you can.** Nothing below writes to `/data`, but a phone in this state is not the moment to find out.

## What not to do

* **Never choose "Factory data reset", "Wipe data/factory reset" or "Format data"** in any recovery that appears, and do not run
  `fastboot -w`, `fastboot erase userdata` or `fastboot format`. None of them is needed, and they would destroy the data without removing
  the cause.
* Do not flash anything other than `boot` (and optionally `recovery`) for this fix.

## Step 1: check the bootloader message (`misc`)

When Android's `init` gives up (`init_user0_failed` and the like) it writes a request for the bootloader into the `misc` partition and
reboots into the recovery partition. A phone that carries such a request keeps starting its recovery, and a stock recovery then offers
"Factory data reset". Look first, from a recovery that gives root `adb` (here: the custom OrangeFox build):

```
adb shell "head -c 200 /dev/block/bootdevice/by-name/misc | strings"
```

* Nothing printed: no request is pending; skip to step 2. (On the reference phone nothing was printed, probably because the custom recovery
  that had started after the failed boot clears such a request; the four commands were run anyway, harmlessly.)
* A request printed (`boot-recovery`, `--wipe_data`, `--prompt_and_wipe_data ...`): save the first 4096 bytes, then clear the defined
  fields (the first 864 bytes: command 32 + status 32 + recovery 768 + stage 32), and do not start any wipe:

```
adb shell "dd if=/dev/block/bootdevice/by-name/misc of=/tmp/misc-backup.bin bs=4096 count=1"
adb pull /tmp/misc-backup.bin misc-backup.bin
adb shell "dd if=/dev/zero of=/dev/block/bootdevice/by-name/misc bs=864 count=1 && sync && echo CLEARED"
```

To undo, `dd` the backup back. The reference phone ran all four commands (the first one printed nothing).

## Step 2: make the modified boot image

```
python3 tools/add_cmdline.py boot-original.img boot-fixed.img "initcall_blacklist=drv260x_driver_init" --mkbootimg PATH/TO/mkbootimg
```

The script appends the parameter to the image's own command line, packs the image again with every other header field of the original,
then unpacks the result and **checks that kernel, ramdisk and dtb are byte-identical to the original**. If anything differs it deletes
the output and says so. On the reference ROM's boot image it printed:

```
command line before: console=ttyMSM0,115200n8 earlycon=msm_geni_serial,0x880000 androidboot.hardware=qcom androidboot.console=ttyMSM0 service_locator.enable=1 lpm_levels.sleep_disabled=1 loop.max_part=7
command line after : ... loop.max_part=7 initcall_blacklist=drv260x_driver_init
identical to the original: dtb, kernel, ramdisk
boot-fixed.img  16842752 bytes  sha256 4f32c10b9db4f5ca10d7a2f337ea910036e81ec2120991d5767ef1563d0a7a78
```

That sha256 is the image that was flashed on the reference phone. The tool was run with the `mkbootimg` of the OrangeFox 12.1 tree; the
current upstream version was not tried here.

**Check that the parameter can match anything.** `initcall_blacklist` compares the name of the initcall function; a name that does not
exist is ignored without a message. In this kernel the function is `drv260x_driver_init` (generated by `module_i2c_driver(drv260x_driver)`).
From a root shell on the same kernel: `cat /proc/kallsyms | grep drv260x`. If your kernel names it differently, use that name.

## Step 3: try it without writing anything

```
adb reboot bootloader
fastboot boot boot-fixed.img
```

Hold no buttons; wait up to three minutes (the first boot is slow). Expected: the logo, the boot animation, the lock screen with your
usual PIN or pattern, and your data. If the phone does something else, nothing has been written: hold Power until it restarts. Do not
restart the working system with a plain reboot before step 4: it would start the installed, unmodified `boot` again.

## Step 4: make it permanent

```
fastboot flash boot boot-fixed.img
fastboot reboot
```

Only the `boot` partition changes. `/data`, `vbmeta` and the logical partitions (system, vendor, ...) are untouched, and the kernel,
ramdisk and dtb inside `boot` are the official ones. An orange "bootloader unlocked" warning at the start is normal with an unlocked
bootloader. Keep `boot-original.img` and `misc-backup.bin`.

Optional: the same parameter helps a custom recovery. On the reference phone the custom recovery crashed in about half of its boots for
the same reason. The source tree of [hesinj/orangefox-toco](https://github.com/hesinj/orangefox-toco) now carries the parameter
(`BoardConfig.mk`, build `r9`); that build had not been run on the phone when this was written.

## Undo

```
fastboot flash boot boot-original.img
```

After a hardware repair of the bus, flash the original and vibration can work again (and the AW3644 LED driver on the bus can start). Nothing else was changed.

## After a ROM update

An OTA or a ROM zip replaces `boot` with the release's, and the problem returns until the parameter is applied to the **new** boot image.
Before updating: keep the old `boot-original.img`; after: take the new release's boot image, run step 2 on it (check the symbol name in
the new kernel), and flash it. A kernel that renames the init function makes the parameter do nothing, silently.

## What stops working

* Haptic feedback and the vibration effects (they did not work while the chip was silent anyway).
* Nothing else is known to stop working. The phone's flash works (the owner's report; the power-management chip drives it, see
  [2-evidence.md](2-evidence.md)). The AW3644 LED driver on the dead bus fails to start, as it did before the fix; the parameter does not touch it.

## Did it work?

* Right away: Android reaches the lock screen.
* In the kernel log (`adb shell dmesg`): no `drv260x probe` lines and no `Unable to handle kernel paging request`.
* Over days: boot ten times, restart it a few times, and leave it running. The failure used to strike about every other boot.

If Android still dies at random, the haptics driver was not the only writer into freed memory. The method in
[5-method.md](5-method.md) (a console that survives, a debug kernel) is how to find the next one.

# تعمیر، گام‌به‌گام

این همان کاری است که روی گوشی مرجع انجام شد، با بررسی‌هایی که شد. قبل از اجرای هر چیزی همه‌اش را بخوانید.

## پیش از شروع

* **فقط اگر لاگ کرنل الگو را نشان می‌دهد** ([README](../../README.fa.md) را ببینید): خطای I2C روی باس ۳ و probe ناموفق `drv260x`.
  همین نشانه‌ها با لاگ دیگر علت دیگری دارند.
* **بوت‌لودر باز.** تصویر اصلاح‌شده AVB footer ندارد؛ بوت‌لودر باز آن را با هشدار نارنجی بالا می‌آورد، بوت‌لودر قفل نه.
* `adb` و `fastboot` (platform-tools اندروید)، Python 3، و پوشهٔ `mkbootimg` از AOSP
  (`git clone https://android.googlesource.com/platform/system/tools/mkbootimg`؛ درخت OrangeFox 12.1 آن را در `system/tools/mkbootimg` دارد).
* **تصویر boot همان رامی که نصب است**، دقیقاً همان بیلد. روی گوشی مرجع: `boot-toco_20260609_1626.img` از انتشار ۹ ژوئن ۲۰۲۶ (۱۹ خرداد ۱۴۰۵) PixelOS
  (sha256 `6c966951f4a5dda25ff435f05b0e991da31647ccf4b7148690e6f444f1614813`)، که با هش‌گرفتن از هر دو یکی با پارتیشن `boot` نصب‌شده بود.
  اگر فقط پارتیشن را دارید، از آن dump بگیرید (`adb shell dd if=/dev/block/bootdevice/by-name/boot ...` از ریکاوری با adb روت).
* **داده‌هایتان، اگر می‌توانید اول کپی شده باشد.** هیچ‌چیز در ادامه روی `/data` نمی‌نویسد، ولی گوشی‌ای در این وضعیت جای امتحان‌کردن این موضوع نیست.

## کارهایی که نباید کرد

* **هرگز «Factory data reset»، «Wipe data/factory reset» یا «Format data» را** در هیچ ریکاوری‌ای که ظاهر شد انتخاب نکنید، و `fastboot -w`،
  `fastboot erase userdata` یا `fastboot format` را اجرا نکنید. هیچ‌کدام لازم نیست، و داده‌ها را بدون برداشتن علت از بین می‌برند.
* برای این تعمیر چیزی جز `boot` (و اختیاری `recovery`) فلش نکنید.

## گام ۱: پیام بوت‌لودر (`misc`) را بررسی کنید

وقتی `init` اندروید تسلیم می‌شود (`init_user0_failed` و مانند آن) یک درخواست برای بوت‌لودر در پارتیشن `misc` می‌نویسد و به پارتیشن ریکاوری ریستارت می‌کند. گوشی‌ای که
چنین درخواستی دارد مدام ریکاوری‌اش را بالا می‌آورد، و ریکاوری استاندارد بعد «Factory data reset» پیشنهاد می‌دهد. اول نگاه کنید، از ریکاوری‌ای که adb روت می‌دهد
(اینجا: ساخت سفارشی OrangeFox):

```
adb shell "head -c 200 /dev/block/bootdevice/by-name/misc | strings"
```

* چیزی چاپ نشد: درخواستی در انتظار نیست؛ به گام ۲ بروید. (روی گوشی مرجع چیزی چاپ نشد، احتمالاً چون ریکاوری سفارشی‌ای که بعد از بوت ناموفق بالا آمده بود چنین
  درخواستی را پاک می‌کند؛ چهار دستور به هر حال اجرا شد، بی‌ضرر.)
* درخواستی چاپ شد (`boot-recovery`، `--wipe_data`، `--prompt_and_wipe_data ...`): ۴۰۹۶ بایت اول را ذخیره کنید، بعد فیلدهای تعریف‌شده را پاک کنید (۸۶۴ بایت اول:
  command ‏۳۲ + status ‏۳۲ + recovery ‏۷۶۸ + stage ‏۳۲)، و هیچ پاک‌سازی‌ای را شروع نکنید:

```
adb shell "dd if=/dev/block/bootdevice/by-name/misc of=/tmp/misc-backup.bin bs=4096 count=1"
adb pull /tmp/misc-backup.bin misc-backup.bin
adb shell "dd if=/dev/zero of=/dev/block/bootdevice/by-name/misc bs=864 count=1 && sync && echo CLEARED"
```

برای برگرداندن، نسخهٔ پشتیبان را با `dd` برگردانید. گوشی مرجع هر چهار دستور را اجرا کرد (اولی چیزی چاپ نکرد).

## گام ۲: تصویر boot اصلاح‌شده را بسازید

```
python3 tools/add_cmdline.py boot-original.img boot-fixed.img "initcall_blacklist=drv260x_driver_init" --mkbootimg PATH/TO/mkbootimg
```

اسکریپت پارامتر را به خط فرمان خودِ تصویر اضافه می‌کند، تصویر را با همهٔ فیلدهای دیگر header اصلی دوباره می‌بندد، بعد نتیجه را باز می‌کند و **بررسی می‌کند که کرنل،
ramdisk و dtb بایت‌به‌بایت با اصل یکی باشند**. اگر چیزی فرق کند خروجی را پاک می‌کند و می‌گوید. روی تصویر boot رام مرجع این را چاپ کرد:

```
command line before: console=ttyMSM0,115200n8 earlycon=msm_geni_serial,0x880000 androidboot.hardware=qcom androidboot.console=ttyMSM0 service_locator.enable=1 lpm_levels.sleep_disabled=1 loop.max_part=7
command line after : ... loop.max_part=7 initcall_blacklist=drv260x_driver_init
identical to the original: dtb, kernel, ramdisk
boot-fixed.img  16842752 bytes  sha256 4f32c10b9db4f5ca10d7a2f337ea910036e81ec2120991d5767ef1563d0a7a78
```

این sha256 همان تصویری است که روی گوشی مرجع فلش شد. ابزار با `mkbootimg` درخت OrangeFox 12.1 اجرا شد؛ نسخهٔ فعلی upstream اینجا امتحان نشد.

**بررسی کنید پارامتر با چیزی بخواند.** `initcall_blacklist` نام تابع initcall را مقایسه می‌کند؛ نامی که وجود نداشته باشد بدون هیچ پیامی نادیده گرفته می‌شود. در این کرنل
تابع `drv260x_driver_init` است (تولیدشده توسط `module_i2c_driver(drv260x_driver)`). از شل روت روی همان کرنل: `cat /proc/kallsyms | grep drv260x`. اگر کرنل شما نام
دیگری دارد، همان را بنویسید.

## گام ۳: بدون نوشتن چیزی امتحانش کنید

```
adb reboot bootloader
fastboot boot boot-fixed.img
```

هیچ دکمه‌ای نگه ندارید؛ تا سه دقیقه صبر کنید (بوت اول کند است). انتظار: لوگو، انیمیشن بوت، قفل‌صفحه با PIN یا الگوی همیشگی، و داده‌هایتان. اگر گوشی کار دیگری
کرد، چیزی نوشته نشده: Power را نگه دارید تا ریستارت شود. پیش از گام ۴ سیستمِ در حال کار را با ریبوت ساده ریستارت نکنید: `boot` نصب‌شدهٔ بدون تغییر را دوباره بالا می‌آورد.

## گام ۴: دائمی کنید

```
fastboot flash boot boot-fixed.img
fastboot reboot
```

فقط پارتیشن `boot` عوض می‌شود. `/data`، `vbmeta` و پارتیشن‌های منطقی (system، vendor، ...) دست‌نخورده‌اند، و کرنل، ramdisk و dtb داخل `boot` همان رسمی‌ها هستند.
هشدار نارنجی «bootloader unlocked» در شروع با بوت‌لودر باز طبیعی است. `boot-original.img` و `misc-backup.bin` را نگه دارید.

اختیاری: همین پارامتر به ریکاوری سفارشی هم کمک می‌کند. روی گوشی مرجع ریکاوری سفارشی در حدود نیمی از بوت‌ها به همین دلیل کرش می‌کرد. درخت منبع
[hesinj/orangefox-toco](https://github.com/hesinj/orangefox-toco) حالا پارامتر را دارد (`BoardConfig.mk`، بیلد `r9`)؛ آن بیلد تا زمان نوشتن این متن روی گوشی اجرا نشده بود.

## برگرداندن

```
fastboot flash boot boot-original.img
```

بعد از تعمیر سخت‌افزاریِ باس، تصویر اصلی را فلش کنید تا لرزش دوباره بتواند کار کند (و درایور LED با نام AW3644 روی باس هم بتواند راه بیفتد). چیز دیگری عوض نشده بود. اگر دور زدن دوربین در [6-camera.md](6-camera.md) را هم اعمال کرده بودید، ایمیج اصلی آن را هم برمی‌دارد.

## بعد از آپدیت رام

OTA یا zip رام، `boot` را با نسخهٔ رسمی جایگزین می‌کند و مشکل برمی‌گردد، تا وقتی پارامتر روی تصویر boot **جدید** دوباره گذاشته شود. پیش از آپدیت: `boot-original.img` قدیمی را نگه دارید؛
بعد از آن: تصویر boot انتشار جدید را بگیرید، گام ۲ را روی آن اجرا کنید (نام نماد را در کرنل جدید بررسی کنید) و فلشش کنید. کرنلی که نام تابع init را عوض کند، پارامتر را بی‌صدا بی‌اثر می‌کند. دور زدن دوربین در [6-camera.md](6-camera.md) داخل همین ایمیج boot است و همین سرنوشت را دارد: `tools/patch_softflash.py` را روی ایمیج جدید هم اجرا کنید.

## چه چیزی کار نمی‌کند

* بازخورد لرزشی و جلوه‌های لرزش (وقتی چیپ ساکت بود هم کار نمی‌کردند).
* دوربین عقب تا وقتی باس مرده است کرش می‌کند؛ با یک دور زدن جدا در کرنل درست می‌شود، [6-camera.md](6-camera.md).
* چیز دیگری که از کار بیفتد شناخته نشده است. فلش گوشی کار می‌کند (گزارش صاحب گوشی؛ چیپ مدیریت توان آن را راه می‌اندازد،
  [2-evidence.md](2-evidence.md) را ببینید). درایور LED با نام AW3644 روی باس خراب مثل قبل از تعمیر راه نمی‌افتد؛ پارامتر به آن دست نمی‌زند.

## آیا جواب داد؟

* بلافاصله: اندروید به قفل‌صفحه می‌رسد.
* در لاگ کرنل (`adb shell dmesg`): هیچ خط `drv260x probe` و هیچ `Unable to handle kernel paging request` نیست.
* در طول چند روز: ده بار بوت کنید، چند بار ریستارت کنید، و روشن بگذارید. خرابی قبلاً تقریباً هر بار دوم می‌زد.

اگر اندروید باز هم تصادفی می‌میرد، درایور لرزش تنها نویسنده روی حافظهٔ آزاد نبوده است. روش [5-method.md](5-method.md) (یک کنسول که باقی بماند، یک کرنل اشکال‌یاب) راهی است
برای پیدا کردن نفر بعدی.
